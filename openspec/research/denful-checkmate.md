# `denful/checkmate`  -  primary-source research

Scope: research the `denful/checkmate` flake-checker from primary sources
only (docs site page, upstream repo tree at HEAD, and the existing
`nix-lib` `modules/_dev/module.nix` for comparison). Goal: decide
whether checkmate simplifies, complements, or duplicates the existing
7-backend check aggregation in nix-lib.

All citations point at either the docs site
(`https://denful.dev/ecosystem/checkmate/`), or the upstream repo
`denful/checkmate` (default branch `main`, tree SHA
`d21a2006c0346d3ad522f6c68ce4401e848a7157` at time of research, from
`gh api repos/denful/checkmate/git/trees/HEAD?recursive=1`), or the
local `nix-lib` tree.

Note on ownership: the repo README and every internal template still
uses the historical `github:vic/checkmate` URL, but the docs page and
GitHub redirect resolve to `denful/checkmate` (same rename pattern as
`vic/import-tree` → `denful/import-tree`).

---

## 1. What it is, one sentence

> "A flake checker (treefmt & nix-unit) for testing other flakes with
> zero dependencies."
> (`gh api repos/denful/checkmate` → `description`.)

Docs page framing (`https://denful.dev/ecosystem/checkmate/`):

> "checkmate bundles treefmt and nix-unit into a reusable CI pipeline
> for any Nix flake."

Concretely, checkmate is *itself* a flake. You point it at *your*
flake via `--override-input target .` (or via a follow), and its
`nix flake check` output runs formatting + unit tests against your
tree. It is not a library you import; it is a flake you invoke.

## 3. `flake.nix`  -  the entry point

Complete, verbatim (`gh api repos/denful/checkmate/contents/flake.nix`):

```nix
# DO-NOT-EDIT. This file was auto-generated using github:vic/flake-file.
# Use `nix run .#write-flake` to regenerate it.
{
  outputs = inputs: inputs.flake-parts.lib.mkFlake { inherit inputs; } (inputs.import-tree ./modules);

  inputs = {
    flake-file.url = "github:vic/flake-file";
    flake-parts = {
      inputs.nixpkgs-lib.follows = "nixpkgs-lib";
      url = "github:hercules-ci/flake-parts";
    };
    import-tree.url = "github:vic/import-tree";
    nix-unit = {
      inputs = {
        flake-parts.follows = "flake-parts";
        nixpkgs.follows = "nixpkgs";
      };
      url = "github:nix-community/nix-unit";
    };
    nixpkgs.url = "github:nixos/nixpkgs/nixpkgs-unstable";
    nixpkgs-lib.follows = "nixpkgs";
    systems.url = "github:nix-systems/default";
    target.url = "github:vic/checkmate?dir=templates/success";
    treefmt-nix = {
      inputs.nixpkgs.follows = "nixpkgs";
      url = "github:numtide/treefmt-nix";
    };
  };
}
```

Key facts:

- checkmate is a **flake-parts flake** built via dendritic
  (`inputs.import-tree ./modules`). Same authorial pattern as
  `import-tree`, `flake-file`, `den`, etc.
- `inputs.target` is the flake being tested. Default is
  `templates/success` (a fixture). Consumers override via
  `--override-input target .` or a `follows`.
- Real inputs (with `flake.lock` verified):
  `flake-file`, `flake-parts`, `import-tree`, `nix-unit`, `nixpkgs`,
  `nixpkgs-lib` (follows `nixpkgs`), `systems`, `target`, `treefmt-nix`.
  Nine flake nodes total in `flake.lock`.

## 5. The six modules  -  verbatim, in order

### 5.1 `modules/flakeModule.nix`

Exports `flake.flakeModule` for consumers who want to *reuse* the
checkmate module inside their own flake (as opposed to running it
against their flake from the outside):

```nix
{
  flake.flakeModule =
    { inputs, lib, ... }:
    {
      imports = [
        (inputs.flake-file.flakeModules.dendritic or { })
        (inputs.import-tree ./checkmate)
      ];

      flake-file.inputs.checkmate = {
        url = lib.mkDefault "github:vic/checkmate";
        inputs = {
          flake-file.follows = "flake-file";
          flake-parts.follows = "flake-parts";
          import-tree.follows = "import-tree";
          nix-unit.follows = "nix-unit";
          nixpkgs.follows = "nixpkgs";
          nixpkgs-lib.follows = "nixpkgs";
          systems.follows = "systems";
          target.follows = "target";
          treefmt-nix.follows = "treefmt-nix";
        };
      };
    };
}
```

Note: `flake.flakeModule` is a **single** flake-parts module. Consumers
that already run flake-parts can `imports = [ inputs.checkmate.flakeModule ]`
and inherit treefmt + nix-unit wiring. This is the composition path
if we ever want to reuse it inside nix-lib.

### 5.2 `modules/imports.nix`  -  the `target` extension hook

```nix
{ inputs, ... }:
let
  im =
    sub:
    let
      path = "${inputs.target}/${sub}";
    in
    if builtins.pathExists path then inputs.import-tree path else { };
in
{
  imports = [
    (im "checkmate.nix")
    (im "checkmate/modules")
  ];
}
```

This is the extensibility contract. checkmate imports two paths from
inside the `target` flake if they exist:

- `<target>/checkmate.nix`  -  a single flake-parts module.
- `<target>/checkmate/modules/`  -  a dendritic tree of flake-parts modules.

So a consumer flake can *add* checks, treefmt formatters, custom
`nix-unit` config, or anything else expressible as a flake-parts
module, simply by dropping files under `checkmate/modules/` in
their own repo. See §5.7 for the template that demonstrates this.

### 5.3 `modules/templates.nix`

```nix
{
  flake.templates.default = {
    description = "Success";
    path = ../templates/success;
  };
  flake.templates.dendritic = {
    description = "Dendritic";
    path = ../templates/dendritic;
  };
}
```

Two templates. `success` is the CI fixture (minimal). `dendritic` is
what `nix flake new -t github:vic/checkmate` installs.

### 5.4 `modules/checkmate/dendritic.nix`

```nix
{ inputs, lib, ... }:
{
  flake-file.inputs.flake-file.url = lib.mkDefault "github:vic/flake-file";
  imports = [
    (inputs.flake-file.flakeModules.dendritic or { })
  ];
}
```

Enables the `flake-file` dendritic flake-module (auto-generates
`flake.nix` from the module tree). Not required to run checkmate; it
just wires `flake-file` support so the auto-generated `flake.nix`
pattern works.

### 5.5 `modules/checkmate/nix-unit.nix`

```nix
{ inputs, lib, ... }:
{
  flake-file.inputs.nix-unit = {
    url = lib.mkDefault "github:nix-community/nix-unit";
    inputs.nixpkgs.follows = lib.mkDefault "nixpkgs";
    inputs.flake-parts.follows = lib.mkDefault "flake-parts";
  };

  imports = [
    (inputs.nix-unit.modules.flake.default or { })
  ];

  perSystem =
    { lib, ... }:
    {
      nix-unit = {
        allowNetwork = lib.mkDefault true;
        inputs = lib.mkDefault inputs;
      };
    };
}
```

**Load-bearing detail**: checkmate does **not** implement its own
test runner. It defers entirely to `nix-unit.modules.flake.default`,
which is the flake-parts module exported by `nix-community/nix-unit`.
That module ingests `flake.tests` from the consumer (via
`inputs.target`) and produces `checks.<system>.nix-unit`.

The `perSystem.nix-unit.inputs = lib.mkDefault inputs` line hands
checkmate's own `inputs` (including `inputs.target`) to nix-unit so
that tests can reference `inputs.target.<anything>`.

### 5.6 `modules/checkmate/target.nix`

```nix
{ lib, ... }:
{
  flake-file.inputs.target.url = lib.mkDefault "github:vic/checkmate?dir=templates/success";
}
```

Default target when nobody overrides. The `success` fixture.

### 5.7 `modules/checkmate/treefmt.nix`

The largest of the six modules:

```nix
{ inputs, lib, ... }:
{
  flake-file.inputs.treefmt-nix = {
    url = lib.mkDefault "github:numtide/treefmt-nix";
    inputs.nixpkgs.follows = lib.mkDefault "nixpkgs";
  };

  imports = [
    (inputs.treefmt-nix.flakeModule or { })
  ];

  perSystem =
    { self', lib, ... }:
    {
      packages.fmt = self'.formatter;
      treefmt = {
        projectRoot = inputs.target;
        projectRootFile = "flake.nix";
        programs = {
          mdformat.enable = lib.mkDefault true;
          yamlfmt.enable = lib.mkDefault true;
          nixfmt.enable = lib.mkDefault true;
          deadnix.enable = lib.mkDefault true;
          nixf-diagnose.enable = lib.mkDefault true;
          prettier.enable = lib.mkDefault true;
        };
        settings.on-unmatched = lib.mkDefault "fatal";
        settings.global.excludes = [
          "LICENSE"
          "flake.lock"
          "*/flake.lock"
          ".envrc"
          ".direnv/*"
          "*/.gitignore"
          ".github/ISSUE_TEMPLATE/*"
        ];
      };
    };
}
```

Six formatters enabled by default: `nixfmt`, `deadnix`,
`nixf-diagnose`, `mdformat`, `yamlfmt`, `prettier`. Every enable
line is `lib.mkDefault`, so a consumer's `checkmate/modules/*.nix`
can `lib.mkForce false` any one. `projectRoot = inputs.target;`
points treefmt at the target flake source (not the checkmate flake).
Exposes `packages.fmt` (the treefmt runner) so
`nix run github:vic/checkmate#fmt --override-input target .` formats
the consumer's tree.

## 6. Public API surface  -  what a consumer can call

From the flake outputs (via `nix flake show` on the flake + inspecting
the module wiring):

- **`checks.<system>.nix-unit`**  -  runs `flake.tests` from
  `inputs.target` via nix-unit. Produced by
  `nix-unit.modules.flake.default`.
- **`checks.<system>.treefmt`**  -  runs treefmt-nix in check mode over
  `inputs.target`. Produced by `treefmt-nix.flakeModule`.
- **`packages.<system>.fmt`**  -  `self'.formatter`, the treefmt
  wrapper. Invoked via `nix run .#fmt` to format the target tree.
- **`formatter.<system>`**  -  set by `treefmt-nix.flakeModule`.
- **`templates.default`**  -  `templates/success` (fixture).
- **`templates.dendritic`**  -  `templates/dendritic` (the one
  `nix flake new` installs).
- **`flake.flakeModule`**  -  a re-usable flake-parts module (§5.1)
  for consumers who want to inline checkmate's wiring instead of
  invoking it as an external flake.

Everything else the consumer gets flows through `inputs.target`:

- **`flake.tests.*`**  -  free-form attrset of
  `{ expr, expected }` pairs on the target flake. nix-unit picks
  them up.
- **`checkmate.nix`** (optional file in target root)  -  a single
  flake-parts module merged into checkmate.
- **`checkmate/modules/**`** (optional directory in target)  -  a
  dendritic tree of flake-parts modules merged into checkmate. See
  the template in §7.

## 7. The `dendritic` template  -  the intended consumer shape

`templates/dendritic/flake.nix`  -  the outer flake the user writes:

```nix
{
  outputs = _: {
    lib.dup = a: a * 2;
  };
}
```

`templates/dendritic/checkmate/`  -  a sub-flake that *is* checkmate,
targeting the parent:

```nix
# templates/dendritic/checkmate/flake.nix (auto-generated)
{
  outputs = inputs: inputs.flake-parts.lib.mkFlake { inherit inputs; } (inputs.import-tree ./modules);
  inputs = {
    checkmate = {
      inputs = {
        flake-file.follows = "flake-file";
        flake-parts.follows = "flake-parts";
        import-tree.follows = "import-tree";
        nix-unit.follows = "nix-unit";
        nixpkgs.follows = "nixpkgs";
        nixpkgs-lib.follows = "nixpkgs";
        systems.follows = "systems";
        target.follows = "target";
        treefmt-nix.follows = "treefmt-nix";
      };
      url = "github:vic/checkmate";
    };
    # ... nixpkgs, flake-parts, target, etc.
    target.url = "github:vic/checkmate?dir=templates/dendritic";
  };
}
```

`templates/dendritic/checkmate/modules/checkmate.nix`  -  wires it:

```nix
{ inputs, ... }:
{
  flake-file.inputs.target.url = "github:vic/checkmate?dir=templates/dendritic";
  imports = [ (inputs.checkmate.flakeModule or { }) ];
}
```

`templates/dendritic/checkmate/modules/test.nix`  -  where tests go:

```nix
{
  flake.tests."test universe works" = {
    expr = 2 * 2;
    expected = 4;
  };
}
```

So the *idiomatic* consumer shape is: **a `checkmate/` sub-flake in
your repo** whose sole purpose is to run checkmate against the parent.
The tests live at `checkmate/modules/*.nix` and set `flake.tests.<name>`.

The `templates/success/` variant is simpler (no sub-flake): the CI
just invokes checkmate as an external flake with
`--override-input target .`, and the consumer's `checkmate/modules/test.nix`
is picked up via the `imports.nix` hook (§5.2).

## 8. How checkmate replaces / augments existing tools

- **Wraps `nix flake check`**: no. checkmate *is* a flake whose
  `checks.<system>` outputs you run via `nix flake check` on
  *checkmate itself*, with your flake supplied as `--override-input target`.
  It does not intercept or re-implement `nix flake check`; it just
  packages the two checks (nix-unit + treefmt) that consumers most
  commonly need.
- **Adds new check types**: no. `checks.<system>.nix-unit` and
  `checks.<system>.treefmt` are the only two outputs. No coverage
  reporter, no HTML output, no JUnit XML, no snapshot backend, no
  BDD, no docs check. It is a **pipeline packaging**, not a check
  engine.
- **Produces reports**: no. Standard `nix flake check` derivation
  succeeds or fails; the output is stderr from `nix-unit` and
  `treefmt`.
- **Owns the checks aggregation**: it *tries* to. Because it wraps
  the target as `inputs.target`, its aggregation is disjoint from
  the target's own `checks.<system>` outputs. You get a **second**
  aggregation ("checkmate's checks against my flake") layered next
  to your own.

## 9. Composition with existing tools

- **`nix-unit`**: checkmate is a thin wrapper on top of
  `nix-unit.modules.flake.default` (§5.5). If nix-lib already uses
  nix-unit directly (which it does, `_dev/module.nix:94-108`), the
  runner is the same code path. checkmate adds no capability.
- **`treefmt-nix`**: checkmate is a thin wrapper on top of
  `treefmt-nix.flakeModule` (§5.7). If nix-lib already imports
  `inputs.treefmt-nix.flakeModule` directly (which it does,
  `_dev/module.nix:21`), the runner is the same code path. checkmate
  adds a formatter default set (nixfmt/deadnix/mdformat/yamlfmt/
  prettier/nixf-diagnose) that nix-lib currently only partially uses
  (`nixfmt` only, `_dev/module.nix:255`).
- **`namaka`**: no support. checkmate has no snapshot testing.
- **`nixtest`**: no support. checkmate hard-codes `flake.tests` as
  the nix-unit interface.
- **`nixt`**: no support. Same reason.
- **`nix-tests`**: no support. Same reason.
- **`lib.debug.runTests`**: no support. checkmate does not expose
  eval-time backends.
- **BDD / docs / scenario / examples**: no support. Any check that
  is not `flake.tests` + `treefmt` requires a custom
  `checkmate/modules/*.nix` module that adds `perSystem.checks.<name>`
  directly (which is exactly what nix-lib already does without
  checkmate).

**Composition verdict**: checkmate can coexist with nix-lib's
7-backend aggregation only by being *ignored* for the six non-nix-unit
backends. It cannot orchestrate namaka, nixtest, nixt, nix-tests,
runTests, or docs; those live in the target's own `checks.<system>`.

## 11. Verdict for nix-lib

**Duplicate, not simplification, not complement.**

Reasoning:

1. nix-lib already imports `treefmt-nix.flakeModule` directly
   (`modules/_dev/module.nix:21`). checkmate's treefmt wiring is
   just `treefmt-nix.flakeModule` with a set of `mkDefault` enables.
   nix-lib can copy those enables into its own treefmt config in
   ~10 lines with zero new flake inputs.
2. nix-lib already runs `nix-unit` directly against its aggregated
   `flake.tests` (`modules/_dev/module.nix:94-108`). checkmate wraps
   `nix-unit.modules.flake.default`, which is a strict subset of
   what nix-lib does (nix-lib also runs 6 *other* backends against
   the same tests).
3. checkmate's core value proposition ("one command, treefmt +
   nix-unit for any flake") targets flakes that currently have
   *no* check aggregation. nix-lib has 7 backends + BDD + docs +
   scenarios + examples. The delta checkmate would provide is
   *negative*: adopting it means running nix-lib's checks through
   a wrapper that only understands 2 of the 7 backends.
4. The `inputs.target` indirection is actively harmful for a
   library flake: it inverts the ownership so that checkmate's
   flake owns the `checks.<system>` outputs, not nix-lib. A
   downstream consumer running `nix flake check nix-lib` would
   still see nix-lib's own aggregation, not checkmate's. Two
   competing aggregations is worse than one.
5. checkmate is Apache-2.0. nix-lib is MIT (verify separately).
   If we adopted checkmate as a flake input, the transitive-license
   surface grows; if we vendored, we would need to preserve
   Apache-2.0 attribution. Not blocking, but noise for a component
   we do not need.

**One niche where checkmate might help**: as a *template* for
downstream consumers of nix-lib who want a fast "opinionated CI in
one file" story. We could ship a `templates/checkmate.nix`
demonstrating how to plug nix-lib output into checkmate for
consumers who want treefmt+nix-unit without inheriting nix-lib's
full 7-backend setup. This is a documentation/template question,
not an internal-adoption question.

## 12. Integration sketch (only if we changed our mind)

Not recommended, but for completeness: the minimum-friction way to
adopt would be to *not* replace `_dev/module.nix`, but to publish
nix-lib's `flake.tests` (which we already do via the option in
`_dev/module.nix:27-32`) and let downstream users run

```console
nix flake check github:denful/checkmate --override-input target github:Dauliac/nix-lib
```

against us from the outside. That requires **zero code changes** in
nix-lib. If someone actually wants that, we document the invocation
in the README and move on. No file changes, no lock churn, no
migration.

If we wanted to *internally use* checkmate (still not recommended),
the migration path would be:

1. Add `checkmate.url = "github:denful/checkmate"` to
   `modules/_dev/flake.nix` inputs.
2. In `modules/_dev/module.nix`, replace the treefmt-nix import with
   `inputs.checkmate.flakeModule` and drop the local treefmt config.
3. Keep the 6 non-nix-unit backend checks as-is (checkmate cannot
   drive them).
4. Accept +7 transitive flake inputs (`flake-file`, `import-tree`,
   `systems`, `nixpkgs-lib` alias, `target`, `nix-github-actions`,
   plus the ambient `flake-parts` follow).

The cost is 7 lock entries + Apache-2.0 attribution in exchange for
saving ~10 lines of treefmt config. Not worth it.
